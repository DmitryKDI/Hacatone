## Как повторить и собрать журнал

1. Подготовьте `.env`, локальные PDF и корпус по [README](../../README.md). Для сквозного прогона запустите заглушки ML и ТОиР на портах 8001 и 8002 по той же инструкции.
2. Из корня репозитория запустите приложение с записью stderr.

   ```powershell
   New-Item -ItemType Directory -Force dist | Out-Null
   .\.venv\Scripts\python.exe -m uvicorn mechanic.app:app --host 127.0.0.1 --port 8000 --log-level info 2> dist/agent.log
   ```

3. На `http://127.0.0.1:8000` выберите `E549YT198 / S-0011`, запустите диагностику, спросите «Как контролировать уровень масла после остановки двигателя?» и запросите предпросмотр заявки на контроль уровня. Для отладки поиска и черновика достаточно остановиться на предпросмотре. Отправку проверяйте отдельным подтверждением на локальной заглушке.
4. В панели **Network** браузера откройте соответствующий `POST /api/action` или `POST /api/send` и скопируйте заголовок ответа `X-Action-Id`. Диагностика, вопрос, предпросмотр и подтверждение имеют разные идентификаторы. В другом терминале отфильтруйте журнал.

   ```powershell
   $actionId = 'значение X-Action-Id'
   Select-String -LiteralPath dist/agent.log -SimpleMatch $actionId | ForEach-Object { $_.Line }
   ```

Для локальной регрессии из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m mechanic.evaluate
node --test tests/frontend.test.cjs
```

`mechanic.evaluate` измеряет поиск и серверные отказы. Семантику реальной модели показывает отдельно сохранённый контрольный прогон.

## Куда смотреть при сбое

| Симптом | События журнала и следующий шаг |
|---|---|
| Диагностика не дошла до рекомендаций | Проверьте `ml.result`. При `normal` и `check_failed` отсутствие `llm.request` ожидаемо. При ошибке подключения проверьте `MOCK_ML_URL` и доступность заглушки. |
| Нет подходящего источника | Сопоставьте `agent.tool` и `search.result`. Проверьте двигатель, физические страницы и актуальность корпуса. При изменении PDF перестройте индекс и повторите сверку нормативов. |
| Модель не ответила или вернула неполный результат | В `llm.request` смотрите `stage`, `http`, `outcome`, `attempt` и `elapsed_ms`. Стадия `decide` выбирает инструмент и ответ, `verify` сверяет основания. `truncated` означает ограничение ответа, `network_error` — ошибку связи или таймаут. |
| Источник найден, но ответ заблокирован | В `verify.result` сравните `checked`, `invalid`, `supported` и `comparison`. `agent.revise` показывает попытку исправления. При `agent.conflict` сверяйте обе физические страницы и применимость к фактической комплектации. |
| Номер заявки не появился | У `/api/send` найдите `toir.submit`, затем `toir.result`. `created` подтверждает успех. При `unconfirmed` сначала проверьте результат в ТОиР: автоматический повтор может создать дубль. |

К отчёту об ошибке приложите SHA коммита, пару машина/проверка, шаг, время с часовым поясом, HTTP-статус, `X-Action-Id` и события по этому ID. В [сводке](dima-debug-summary.json) сохранены отобранные технические поля. Исходные ответы модели, выдержки из руководств, ключи, cookie и токены подтверждения хранятся вне Git.
