# Spec Delta

## Purpose

Позволяет выбирать OpenAI API, Yandex AI Studio или GigaChat без изменения правил диагностики, источников и заявок.

> В ветке `luna` требования к провайдеру заданы в [отдельном ТЗ](../../../use-luna-provider/specs/llm-providers/spec.md). Ниже сохранена спецификация многопровайдерной версии.

## ADDED Requirements

### Requirement: Явный выбор провайдера
Приложение SHALL поддерживать OpenAI API по умолчанию и выбирать Yandex AI Studio или GigaChat через настройки запуска. Конкретная модель SHALL задаваться отдельно для каждого провайдера. Автоматическая смена провайдера MUST NOT происходить скрыто.

#### Scenario: Основной OpenAI
- **WHEN** выбран OpenAI и предоставлены пригодные учётные данные и доступная модель
- **THEN** генерация выполняется через официальный OpenAI API

#### Scenario: Выбор Yandex
- **WHEN** оператор выбирает Yandex и предоставляет его учётные данные и модель
- **THEN** тот же пользовательский сценарий работает через Yandex без переиндексации руководств и изменения правил заявок

#### Scenario: Выбор GigaChat 3 Ultra
- **WHEN** задан `LLM_PROVIDER=gigachat` и доступна модель GigaChat 3 Ultra
- **THEN** агент использует GigaChat для решений и независимой проверки оснований с сохранением серверных запретов

### Requirement: Отдельные учётные данные API
Приложение SHALL использовать серверные API-ключи выбранного провайдера. Вход в Codex Desktop или подписка ChatGPT MUST NOT трактоваться как наличие API-ключа, оплаченного API-баланса или разрешения использовать пользовательскую веб-сессию ChatGPT.

#### Scenario: Нет API-ключа
- **WHEN** для выбранного провайдера отсутствуют необходимые учётные данные
- **THEN** приложение сообщает оператору причину недоступности генерации без подстановки веб-сессии ChatGPT и без показа секретов в браузере

### Requirement: Общие ограничения генерации
Для всех провайдеров ответы SHALL подчиняться требованиям применимости руководств, качества записи, подтверждения источников и команды механика. Текст модели MUST NOT самостоятельно разрешать вызов ТОиР или обходить серверные проверки.

#### Scenario: Модель предлагает отправить заявку
- **WHEN** ответ любого провайдера содержит предложение отправить заявку без подтверждения
- **THEN** приложение не вызывает ТОиР до команды механика и успешной проверки черновика

### Requirement: Общий контракт выбора инструментов
Все адаптеры SHALL поддерживать выбор ML, RAG и ТОиР по контексту с общими аргументами и результатами. Допускается native tool calling или валидируемое структурированное решение с закрытым списком инструментов. Сервер SHALL ограничивать шаги и время цикла; произвольный текст MUST NOT исполняться. Проверки источников и подтверждения SHALL сохраняться при смене провайдера.

#### Scenario: Одинаковый набор инструментов
- **WHEN** оператор меняет провайдера и повторяет диагностику, вопрос по руководству и подтверждённую заявку
- **THEN** агент выбирает необходимые инструменты по контексту, трассы и серверные запреты проверяются одним контрактным набором

### Requirement: Авторизация GigaChat
Адаптер SHALL получать ключ и область доступа из окружения или локального `.env`. TLS SHALL проверяться. OAuth-токен SHALL храниться в памяти и обновляться при истечении. Ключ, токен и содержимое ответа авторизации MUST NOT попадать в клиент, журнал или репозиторий.

#### Scenario: Истёкший токен
- **WHEN** GigaChat отклоняет кэшированный токен с HTTP 401
- **THEN** адаптер обновляет токен и выполняет не более одной повторной попытки в рамках общего лимита

### Requirement: Ошибки и ограничения API
При таймауте, превышении квоты, ошибке авторизации, недоступности модели или доступа приложение SHALL показывать понятную ошибку. Генерация MUST NOT подменяться фиктивным ответом или приводить к отправке заявки. Повторные попытки SHALL быть ограничены.

#### Scenario: Квота или сеть недоступны
- **WHEN** выбранный LLM API не может выполнить запрос
- **THEN** приложение сообщает об ограничении и не показывает неподтверждённый диагноз как готовый результат

#### Scenario: Непригодный формат ответа
- **WHEN** модель вернула результат, не проходящий проверку структуры черновика или источников
- **THEN** приложение не разрешает отправку такой заявки и сообщает, что результат не удалось подготовить корректно

### Requirement: Стоимость и условия эксплуатации
Инструкция запуска SHALL описывать раздельную оплату API, выбранные модели, пример расчёта расходов, ссылки на актуальные тарифы и ограничения доступа. Стоимость SHALL обозначаться оценкой, зависящей от фактических токенов, модели и повторов.

#### Scenario: Подготовка запуска оператором
- **WHEN** оператор следует инструкции запуска
- **THEN** он может определить необходимые ключи, расходы и ограничения выбранного провайдера до использования платной генерации

### Requirement: Журнал исполнения агента
Сервер SHALL писать в журнал шаги агента, результаты инструментов и проверки источников, исход отправки в ТОиР, время и токены, возвращённые LLM API. События одного действия SHALL иметь общий идентификатор. Ключи, текст запросов и руководств, ответы модели и токены подтверждения SHALL NOT попадать в журнал.

#### Scenario: Отладка сквозного обращения
- **WHEN** механик запускает диагностику, запрашивает рекомендацию и подтверждает заявку
- **THEN** по журналу можно установить порядок шагов, исход и число токенов по вызовам API, не читая содержимое диалога
