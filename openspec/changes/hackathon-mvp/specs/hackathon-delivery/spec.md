# Spec Delta

## Purpose

Определяет проверяемый комплект сдачи хакатонного прототипа и условия его воспроизводимой демонстрации на предоставленных организатором данных.

## ADDED Requirements

### Requirement: Воспроизводимый локальный запуск
Комплект SHALL содержать README с ОС, версиями зависимостей, получением материалов, подготовкой корпуса, настройкой API и запуском приложения/заглушек. Запуск подготовленной поставки SHALL занимать до пяти минут; холодная подготовка SHALL измеряться и описываться отдельно. Если проверка требует холодного запуска за пять минут, несоответствие SHALL фиксироваться до сдачи. Публичный стенд не обязателен.

#### Scenario: Повторный запуск по README
- **WHEN** проверяющий получает репозиторий и предусмотренные организатором материалы и выполняет README с пригодными API-данными
- **THEN** он может запустить продукт локально и пройти основной сценарий без неописанных действий автора

### Requirement: Репозиторий и раскрытие компонентов
Сдача SHALL содержать ссылку на открытый репозиторий с историей коммитов с начала работы. Описание SHALL перечислять вошедшие в продукт библиотеки, фреймворки, модели, API и ранее созданные наработки; использование SHALL соответствовать их лицензиям. Секреты MUST NOT публиковаться.

#### Scenario: Проверка комплекта сдачи
- **WHEN** проверяющий открывает репозиторий и описание продукта
- **THEN** ему доступны история изменений, список сторонних компонентов и сведения для запуска без опубликованных API-ключей

### Requirement: Запрет публичного размещения руководств и индексов
PDF заводских руководств и RAG-индексы с извлечёнными текстами MUST NOT размещаться в открытых репозиториях, включая их историю, LFS и релизы. Их текстовые выгрузки, дампы и архивы MUST NOT обходить запрет. README SHALL описывать отдельное получение PDF и локальную подготовку корпуса; готовый текстовый индекс MUST NOT публиковаться для ускорения запуска.

#### Scenario: Подготовка публичного репозитория
- **WHEN** команда готовит публикацию
- **THEN** проверены исключения Git, отслеживаемые файлы, публикуемая история, LFS и релизы; при обнаружении запрещённых материалов публикация остановлена до исправления

#### Scenario: Запуск из чистой копии
- **WHEN** проверяющий получает публичный репозиторий без PDF и текстового индекса
- **THEN** README позволяет отдельно получить материалы от организатора и построить индекс локально; холодная подготовка измерена отдельно от пятиминутного запуска подготовленного приложения

### Requirement: Обязательное демонстрационное видео
Видео SHALL длиться не более трёх минут, быть записано одним фрагментом без монтажа и показывать продукт на данных задачи: отклонение с риском и страницами руководства с последующей заявкой, вопрос по базе знаний и сбой записи.

#### Scenario: Три эпизода в одной записи
- **WHEN** команда записывает финальное видео
- **THEN** в одной непрерывной записи до трёх минут видны обоснованная заявка с номером ТОиР, ответ с источником и предложение повторить неудачную запись без диагноза

### Requirement: Короткий ролик и согласование сдачи
Комплект SHALL дополнительно включать ролик о работе агента до 60 секунд по ТЗ v6 и описанию кейса. Он MUST NOT заменять непрерывное видео С1–С3. Расхождения длительности и критериев оценки SHALL сверяться с формой сдачи и положением по реестру design.md; команда MUST NOT считать вес ролика однозначно заданным.

#### Scenario: Подготовка двух записей
- **WHEN** команда собирает комплект сдачи
- **THEN** отдельно проверены полная непрерывная запись до трёх минут и короткий ролик до 60 секунд, ссылки и назначение каждого материала понятны проверяющему

### Requirement: Проверка поведения продукта
Готовность SHALL подтверждаться собственными проверками сквозного сценария и контрольных веток на всех группах двигателей. Прохождение тестов организаторских заглушек MUST NOT считаться достаточной проверкой приложения.

#### Scenario: Приёмка перед записью
- **WHEN** команда готовит прототип к сдаче
- **THEN** она проверяет норму, отклонение, сбой, непригодное качество, помехи/низкую уверенность, отсутствие инструкции, запрет чужих источников и ошибки внешних API

### Requirement: Ранний сквозной проход
План SHALL предусматривать первый сквозной проход в часы 12–16 на одной реальной проверке, одном руководстве и одном доступном LLM-провайдере по разделу 10 design.md. Все запреты диагностики и необоснованных работ SHALL действовать уже здесь. Проход MUST NOT считаться завершением P0: полный сценарий SHALL быть собран к 28-му часу; приёмка P0 SHALL включать пороги поиска и смысловую проверку manual-grounded-assistance.

#### Scenario: Контрольная точка 16-го часа
- **WHEN** команда оценивает первый сквозной проход
- **THEN** на выданных данных без подставленных ответов или номеров проходят ML, объяснение с выдержкой и страницей, вопрос, предпросмотр, команда механика и получение номера ТОиР; сбой записи запрещает диагноз и заявку; при провале сначала устраняется блокер цепочки, затем продолжается расширение

### Requirement: Соблюдение периода реализации
Компоненты конкурсного продукта, включая код, настройки, промпты и поисковые индексы, SHALL создаваться в разрешённый период спринта по положению. До старта допускается согласованное текстовое планирование; создание этих OpenSpec-артефактов MUST NOT автоматически запускать реализацию.

#### Scenario: План согласован до спринта
- **WHEN** подготовлены предложение, спецификации, архитектура и задачи
- **THEN** код продукта и его исполняемые настройки не создаются без отдельной команды пользователя и наступления разрешённого периода
