## Goals / Non-Goals

**Goals:**

- Минимизировать число процессов продукта: один сервер приложения плюс неизменённые заглушки организатора.
- Держать применимость источников и право отправки заявки вне произвольного текста LLM.
- Сохранить локальный корпус и поиск при смене LLM API.
- Получить первый работающий сквозной сценарий на одной реальной проверке и одном руководстве в окне 12–16 часов; к 28-му часу расширить его на весь корпус и парк, затем закрыть P0 и проверить отказы.

**Non-Goals:**

- Не строить собственную акустическую модель, сбор аудио, обработку OBD или прогноз ресурса двигателя.
- Не вводить микросервисную платформу, облачную векторную БД, Redis, сложный агентный фреймворк и автоматическую маршрутизацию между моделями.
- Не обещать промышленную надёжность, автономную ремонтную диагностику или измеренное снижение простоев.
- Не добавлять в P0 постоянную историю заявок, сравнение проверок, голос и интеграцию с производственной ТОиР/1С.

## Decisions

### 1. Один сервер Python и простой веб-интерфейс

Python 3.11, FastAPI, Pydantic, HTTPX, Jinja2 и обычные HTML/CSS/JavaScript. FastAPI обслуживает страницы, чат и действия пользователя; сервер хранит текущий контекст сессии. Выбор машины и проверки сбрасывает старый результат, диалог, черновик и подтверждение. Идентификаторы и контекст проверяются сервером, а не доверяются тексту чата.

Альтернатива — отдельный React-фронтенд и API. Она добавляет сборку и отдельный контракт интерфейса без необходимой для этого MVP выгоды. Streamlit быстрее для первого экрана, но менее удобен для контролируемого предпросмотра и мобильного интерфейса. Docker не является условием запуска; основной путь — воспроизводимый локальный запуск на Windows с явно зафиксированными версиями.

### 2. Компактная схема взаимодействия

```text
Browser --> FastAPI application --> Organizer ML HTTP stub
                  |
                  +--> vehicles.json
                  +--> Local SQLite search <-- PDF extraction / OCR
                  +--> Selected LLM API: OpenAI OR Yandex
                  +--> Validated preview --> User confirmation --> TOiR HTTP stub
```

Внутри приложения достаточно логических модулей загрузки парка, клиентов заглушек, корпуса/поиска, агента, правил заявки и интерфейса. Они не становятся отдельными сервисами. Агент получает три отдельных инструмента: запрос диагностики, поиск по руководствам и создание заявки. LLM выбирает следующий инструмент по текущему запросу и результатам вызовов; ML → RAG → ТОиР не зашивается как единственная цепочка. Вопрос по руководству вызывает RAG без ненужного ML или ТОиР. Цикл ограничен числом шагов и временем; ошибки завершаются понятным сообщением. Оба провайдера возвращают нормализованные решения; если native tool calling недоступен, используется валидируемое структурированное имя инструмента из закрытого списка без исполнения произвольного текста.

Серверные запреты статуса, двигателя, источников и подтверждения детерминированы: F5 не отменяет их. Кнопка диагностики передаёт агенту намерение и выбранную пару; результат и вердикт выводятся в чат. ТОиР исполняется лишь после проверки показанного черновика и команды механика; модель не может выдать себе подтверждение. Для приёмки сохраняются трассы выбора инструментов и причин отказа без ключей и полного корпуса.

### Контракты выданного архива v6

- Адреса: `MOCK_ML_URL=http://127.0.0.1:8001`, `MOCK_TOIR_URL=http://127.0.0.1:8002`; на обоих сервисах `GET /health`. Замена URL не требует редактирования кода.
- ML: `POST /diagnose` с `vehicle_id`, `session_id`; успех 200. Ответ: эти же идентификаторы, `status`, `anomaly_type`, `anomaly_title`, `anomaly_score`, `confidence`, `signal_quality`, `description`, `model_version`. Статусы `normal|anomaly|check_failed`; качество `good|warning|bad`; оценки 0..1 либо null. При normal тип/название null; при check_failed оценки также null и качество bad. null не превращается в 0. Проверять пару идентификаторов и согласованность полей; нарушение контракта не превращать в диагноз.
- ТОиР: `POST /tickets`; обязательны `vehicle_id`, `session_id`, `anomaly_type`, `conclusion`, `urgency` (`low|medium|high`), `operations` (непустой список строк), `spare_parts` (список, может быть пустым), `references` (непустой список `{manual,pdf_page}`). `manual` — обозначение/название из ТЗ, `pdf_page` — физическая страница от 1. Успех только при 201 и валидном `{ticket_id,status:"created"}`. Строки из пробелов и пустые работы приложение отсекает самостоятельно.
- Ошибки: 404 — неизвестная/чужая пара, 422 — схема; README отмечает возможный 400 при неверном JSON/кодировке. Код ТОиР дополнительно возвращает 418 при ошибке схемы со старыми `fault_id`, `diagnosis`, `priority`, `works`, `parts`, `source_pages` или вложенными `document/page`. Это ошибка совместимости без автоматического повтора POST; старые имена не используются для сериализации.
- В `vehicles.json` фактически 50 машин, 195 проверок: 111 normal, 69 anomaly, 15 check_failed; 17 warning. У 12 МАЗ с ЯМЗ-536 `model=null`; отображать карточку без выдуманной модели. Номера латинские, регистр значим; двигатель берётся из карточки. Проверки выбираются из истории, диагноз запрашивается по HTTP, не подменяется результатом из JSON.

Уточнения после повторной сверки README:

- Сервисы не предоставляют API списка машин и истории проверок; источник этих данных — `data/vehicles.json`. Проверки в файле упорядочены от ранней к поздней и содержат `checked_at`, которого нет в ответе ML. `engine_model` также отсутствует в ML-ответе и берётся только из карточки. Запрос `/diagnose` содержит только идентификаторы, без WAV/аудио.
- Для `status=anomaly` допустим `0.5 <= anomaly_score <= 1`; значение ниже 0.5 — противоречивый ответ, а не основание изменить статус на normal. `confidence` имеет отдельную шкалу и проектный порог 0.70. В выданной версии `model_version=mock-v1`; версию сохранять как полученную метаинформацию, не выдавать её за версию обученной командой модели. Ограничение >=0.5 не применяется к normal или null в check_failed.
- Тела запросов ML/ТОиР передаются как JSON в UTF-8. 400 указан README как возможная ошибка разбора, 422 — ошибка валидации; конкретная ошибка JSON может возвращаться фреймворком как 422. Клиент должен безопасно обработать оба статуса, не ожидая единственного кода для любой повреждённой строки. Открытый CORS заглушек не переносит ключи LLM в браузер: HTTP-клиенты остаются на сервере.
- ТОиР проверяет схему и существование пары, но не совпадение anomaly_type с ML, не допустимость заявки при normal/check_failed и не смысл работ/страниц. Приложение проверяет это до POST. Отсутствие API списка заявок не означает обязательную историю в MVP: хранение истории остаётся P1; после перезапуска ТОиР номер может повториться.
- Все 195 результатов заранее записаны, данные и описания синтетические. «Реальный POST», «реальная проверка» и «настоящий номер» в календарном плане означают фактический HTTP-вызов по выданной паре и фактически возвращённый номер заглушки, а не диагностику реального автомобиля или производственную заявку.

Дополнение приёмки в задаче 8.3: отдельно проверить границу anomaly_score (0.49 отклоняется, 0.50 и 1 допустимы; normal ниже 0.5 не становится ошибкой), UTF-8 и ответы 400/404/422/418 без фиктивного успеха. Проверить до сетевого вызова ТОиР запрет подменённого F-кода и заявок по normal/check_failed, даже если внешняя заглушка могла бы принять их формат. Эти проверки не требуют изменять выданные сервисы.

### 3. Локальный корпус с проверяемой страницей

PyMuPDF извлекает текст и страницы, Tesseract с русским языком обрабатывает страницы с изображениями текста. OCR применяется при отсутствии пригодного слоя, а не ко всем документам подряд. Таблицы, десятичные разделители, единицы измерения и применимость иллюстраций проверяются визуально на критических фрагментах. Если данные прочитать надёжно нельзя, агент сообщает ограничение.

SQLite хранит реестр документов и фрагменты. У фрагмента есть точное обозначение документа, физическая страница PDF с нумерацией от 1, текст, признак OCR и применимые двигатели. Фрагменты не теряют границы страниц. Применимость к двигателям задаётся по выданному списку документов, а не угадывается LLM.

Группы корпуса: два документа ЯМЗ-236М2, два ЯМЗ-536, один ЗМЗ-5234.10, один общий для ЗМЗ-40904.10 и ЗМЗ-40905.10. Общий документ не отменяет ограничений конкретной модификации внутри текста.

| `ЯМЗ_236_руководство по РЕМОНТУ.pdf` | 236.01.01 РК, 2014 | 287 |

Во всех файлах есть текстовый слой; эвристика «менее 80 символов» выделила 64 страницы. Это кандидаты на визуальный разбор, не доказательство необходимости OCR: например, PDF-страница 29 ЯМЗ-536 РЭ — повёрнутая схема с подписью; обложка 236 РК читается на изображении, но почти не извлекается. Проверить ориентацию, схемы и таблицы; OCR применять к значимому неизвлекаемому тексту, сохраняя качество. Страница без извлечённого текста не считается пустой.

Внутренняя применимость проверяется не только для УАЗ: документы ЯМЗ-236 охватывают и ЯМЗ-238, ЯМЗ-536 — несколько модификаций. Печатная и PDF-нумерация различаются: в 536 РЭ физическая страница 3 напечатана как 2, в 536 РК есть нумерация модулей; единое смещение не предполагается. Нормативы сохраняются с условиями измерения: эксплуатация и стендовая обкатка — разные режимы даже для одной величины.

Индекс строится после старта спринта по всем шести PDF. Это локальный поисковый индекс, а не вручную написанные ответы для выбранных демонстрационных машин.

По новому требованию организатора PDF заводских руководств и RAG-индексы с извлечёнными текстами запрещено размещать в открытых репозиториях. Для этого проекта все шесть выданных PDF и текстосодержащий SQLite/FTS-корпус хранятся локально. Из публичной поставки также исключаются выгрузки фрагментов/OCR, дампы и архивы этих индексов: смена формата не снимает запрета. README описывает отдельное получение материалов организатора, локальную папку и построение индекса; отсутствие файлов даёт понятную инструкцию подготовки, без автоматической загрузки из публичного репозитория проекта.

На этапе реализации настроить исключения Git для папки руководств и конкретных каталогов корпуса/индексов. Перед публикацией проверить не только .gitignore, но и отслеживаемые файлы, историю публикуемых веток, Git LFS и приложенные к репозиторию архивы/релизы. Наличие ignore-правила не удаляет уже отслеживаемый файл. При обнаружении запрещённых материалов остановить публикацию и определить исправление отдельно, без автоматического переписывания истории. На момент этой правки `git ls-files` не показывает PDF и файлы `*.sqlite`, `*.db`, `*.faiss`, `*.pkl`; это проверка текущего индекса Git, а не аудит истории или удалённого репозитория.

Пятиминутный запуск измеряется после отдельного получения PDF и локальной подготовки корпуса. Публикация готового текстового индекса не используется для ускорения запуска; холодная подготовка воспроизводится и измеряется отдельно. Если форма сдачи требует холодного запуска за пять минут, расхождение уточняется без нарушения запрета публикации.

### 4. Поиск с фильтром двигателя до ранжирования

Начальный поиск — SQLite FTS5/BM25 с нормализацией русских слов и единым способом обработки запроса и корпуса. Запрос использует название неисправности, описание признаков и текущий вопрос. Справочник F01–F14 служит мостом к словам, а не к выдуманным разделам PDF. Вводятся только проверенные после чтения материалов синонимы.

Сначала выбираются документы допустимого двигателя, затем выполняется поиск. Модель получает ограниченный набор фрагментов с идентификаторами и метаданными; соседние страницы добавляются при необходимости завершить реальную процедуру.

После получения PDF вручную подготовить и зафиксировать до настройки поиска контрольный набор минимум из 24 случаев: 16 вопросов с ответом (по четыре на группу двигателей: признаки неисправности, перефразированный вопрос, норматив с единицами, общая процедура) и восемь отрицательных (по два на группу: нет основания в корпусе и похожий материал только для чужого двигателя/модификации). Каждый случай содержит двигатель, вопрос, ожидаемые документ и физическую страницу либо ожидаемый отказ с причиной. Ответы и страницы берутся из реально прочитанных PDF; отсутствие инструкции нельзя устанавливать только пустой выдачей поиска. Один из положительных случаев каждой группы дополнительно проверяет вопрос с опорой на предыдущую реплику. Набор охватывает все шесть документов; недостающий тип материала заменяется подтверждённым примером с записанной причиной. Не менее восьми случаев, по два на группу, оставить для приёмки и не использовать при настройке запросов и синонимов.

Поиск проверяется отдельно от генерации: ожидаемый подтверждающий фрагмент должен попадать в первые пять результатов минимум в 15 из 16 положительных случаев; все случаи с нормативами и все четыре положительных случая отложенной приёмки должны проходить. Для восьми отрицательных случаев в связке поиска и проверки достаточности основания ожидается восемь отказов без использования нерелевантной выдачи; все четыре отложенных отрицательных случая обязательны. Отдельно записываются идентификаторы результатов, попадания, отказы и причины ошибок. Это порог готовности P0, а не доказательство полноты корпуса или правильности любых будущих ответов.

Альтернатива — эмбеддинги и векторный поиск. Они остаются необязательным способом улучшения поиска. При провале порогов исправление поиска входит в P0: сначала проверить извлечение текста, фильтры, нормализацию, синонимы и контекст запроса; затем выбрать минимальное достаточное изменение без замены идентификаторов источников. Нельзя объявлять P0 готовым при провале приёмки или маскировать нерелевантный поиск свободной генерацией.

### 5. Разделение правил и генерации

#### Противоречащие технические инструкции

Новое правило пользователя: при обнаружении противоречащих друг другу технических инструкций агент не должен самостоятельно выбирать одну как бесспорную. Он показывает **обе формулировки**, для каждой — проверяемую выдержку, обозначение документа и физическую страницу PDF, сохраняет числа, единицы и условия. Противоречие отмечается явно, а не скрывается общим отказом или объединением несовместимых указаний. Далее агент рекомендует уточнить корректную инструкцию у специалиста или производителя именно для конкретной модификации ДВС; если модификация или условия неизвестны, это ограничение указывается без догадок.

Проверка смыслового основания должна сопоставлять найденные инструкции между собой, а не только подтверждать каждую по отдельности. Уверенность модели, позиция результата поиска или более поздняя дата документа сами по себе не разрешают снять противоречие. Обе показанные формулировки проходят проверку выдержки и ссылки; нельзя выдумать вторую версию ради сообщения о конфликте. Противоречие может находиться в разных документах или на разных страницах одного руководства.

До уточнения запрещены категоричная рекомендация по спорной инструкции и предпросмотр/отправка черновика с зависящими от неё работами. Само нажатие механиком кнопки подтверждения не устраняет конфликт источников. При этом проверенные противоречащие выдержки с пояснением должны быть показаны: запрет рекомендации не означает скрытие обеих формулировок. Контракт POST /tickets не меняется.

Явно различающиеся модификации или условия измерения не объявляются противоречием, если их применимость однозначно установлена по источникам. Если нельзя установить, относятся ли несовместимые указания к выбранной модификации и одинаковым условиям, агент показывает обе формулировки и неопределённость применимости, рекомендует уточнение и не выбирает спорную норму.

Реализация 5.4 и контрактные проверки завершены, реальные результаты моделей ещё проверяются в открытой 5.7; [отчёт реализации](../../../docs/validation/task-5-4.md). Дополнительные случаи проверяются отдельно от зафиксированного массива из 24 вопросов, без изменения исходных ожидаемых страниц и порогов поиска: конфликт в двух документах; конфликт на двух страницах одного документа; неизвестная применимость к модификации; разные однозначно указанные условия без ложного конфликта. Для конфликтных случаев обязательны обе достоверные формулировки/ссылки, явная отметка противоречия, рекомендация уточнения и отсутствие зависимой заявки. Проверить оба LLM-адаптера, включая попытку отправки после подтверждения механика.

#### Общие проверки ответов и работ

Сервер до генерации разбирает статус и качество. `check_failed` и непригодная запись сразу ведут к просьбе повторить запись и запрету заявки. Норма отображается как отсутствие выявленного отклонения этой проверкой. Заявка по норме запрещена.

Для пригодного отклонения модель формирует понятное объяснение и возможные работы по найденным материалам. Для вопроса механика используется тот же корпус с новым поиском. Числа, процедуры и причинные утверждения должны иметь основание; модель не получает роль самостоятельного диагноста по общим знаниям.

Для каждого технического утверждения модель возвращает отдельно текст, идентификатор переданного фрагмента и подтверждающую выдержку. Сервер восстанавливает документ и страницу из корпуса, проверяет принадлежность фрагмента текущей выдаче и наличие выдержки в нём с нормализацией только пробелов и переносов. Число, единица, диапазон и условие применимости должны сохраняться вместе. Утверждение без такой связи не показывается как рекомендация: вместо него выводится ограничение, а черновик с зависимыми работами блокируется. Совпадение выдержки не доказывает смысловую связь; подтверждение механика также не заменяет проверку источников.

Для P0 работы в заявке собираются сервером из выбранных процедурных выдержек руководства без свободного перефразирования моделью и без добавления операций. Внутренняя связь каждой работы и запчасти с фрагментом, выдержкой, узлом и применимостью сохраняется до отправки; она не добавляет полей в контракт ТОиР. Если из текста нельзя установить операцию, узел или применимость, работа не допускается. Предпросмотр показывает выдержку рядом с работой. Запчасть без такого основания исключается, а при неподтверждённой работе блокируется весь черновик до исправления и нового предпросмотра.

Смысловая приёмка проводится на всех 24 контрольных случаях: вручную сверить каждое техническое утверждение ответа, причину, риск, приоритет и каждую работу/запчасть с PDF, включая числа, единицы, условия и модификацию. Для положительного случая ответ должен содержать ожидаемое основание, а не только отказ. Дополнительно проверить четыре намеренно неверные связки: существующая страница правильного двигателя о другом узле, верная выдержка без основания для предложенной операции, изменённое число/единица и неверная модификация в общем документе. Для допуска P0 нужны ноль неподтверждённых показанных технических утверждений и отправляемых работ во всём наборе, а также блокировка всех четырёх неверных связок. При провале исправляется соответствующая обработка и повторяется затронутая проверка; ручная приёмка не объявляется автоматической гарантией смысла произвольного ответа.

Без достаточного основания показывается отсутствие инструкции и рекомендация дефектовки, отправка блокируется. Общая процедура осмотра допустима только для нужного узла и двигателя с настоящей страницей.

До показа технического ответа и допуска черновика отдельный вызов выбранной LLM проверяет каждую связку «утверждение/работа → выдержка» с контекстом узла и модификации; он получает исходные фрагменты, а не только объяснение генератора. Результат — подтверждено, опровергнуто или недостаточно данных с указанием основания. Сервер допускает только подтверждённые связки, прошедшие также проверку выдержки; при ошибке, таймауте или неоднозначности действует запрет. Одинаковые правила применяются к причинам, рискам, приоритету, операциям и запчастям. Этот дополнительный вызов учитывается в бюджете, таймаутах и длительности видео; он снижает риск, но не заменяет ручную смысловую приёмку и не гарантирует отсутствия ошибок модели.

### 6. Уверенность и приоритет

Не смешивать `confidence`, выраженность отклонения и тяжесть последствий. Контракт задаёт шкалу 0..1; в данных confidence при anomaly 0,48–0,95, у warning 0,48–0,67. Рабочее правило команды: предупреждать при `signal_quality=warning` независимо от числа либо при `confidence<0.70`; это проектный порог, не калиброванная вероятность отказа и не требование заказчика. Ровно 0.70 без warning само по себе предупреждения не вызывает. `bad` и `check_failed` имеют приоритет запрета; null в пригодном anomaly считается некорректным ответом. Правило проверить на всех 195 записях и на граничных значениях, не менять статус на основе anomaly_score.

Предлагаемая командами логика приоритета: высокий — если подходящее руководство подтверждает серьёзный риск и необходимость срочной проверки; низкий — если документация обосновывает плановое действие; средний — консервативный исходный уровень для обоснованной дефектовки без признаков этих двух случаев. Каждое решение объясняется механику. Низкий confidence сам по себе не понижает приоритет. При недостатке источников приоритет не снимает запрета отправки.

Альтернатива — назначать приоритет одной формулой от anomaly_score. Она отвергнута: семантика шкалы и связь с тяжестью не заданы. Предложенное правило не является требованием заказчика и сверяется с полным ТЗ.

### 7. Предпросмотр и отправка заявки

Текущий черновик хранится в серверной сессии вместе с машиной и проверкой. Предпросмотр показывает все обязательные поля, работы, запчасти и источники. Простая кнопка подтверждает показанный состав; изменение контекста аннулирует прежний черновик/подтверждение. Редактирование полей механиком не обязательно для P0.

Перед отправкой сервер проверяет принадлежность проверки машине, пригодное отклонение, тип неисправности из результата, допустимый приоритет, наличие всех полей, непустые работы и источники, существование страниц и двигатель. Для каждой работы проверяется сохранённая связь с процедурной выдержкой, нужным узлом и модификацией по правилам раздела 5; одна существующая страница не разрешает отправку. Список запчастей присутствует даже пустым; артикулы, цены и склад не добавляются без источников.

Только затем сервер вызывает ТОиР и показывает возвращённый номер. Автоматических повторов POST создания нет: таймаут может означать, что заявка создана, но ответ потерян. В этом случае показывается неопределённость. Постоянное хранение и полная защита от повторной отправки остаются P1. Номер TKT не считается глобально уникальным: заглушка после рестарта начинает нумерацию заново.

### 8. Основной OpenAI и сохранённый Yandex

Предусмотреть два небольших адаптера генерации с общей нормализованной структурой результата. Выбор оператора при запуске — OpenAI по умолчанию либо Yandex. Для OpenAI использовать официальный API через сервер с отдельным API-ключом; пользовательское выражение «подключиться к ChatGPT» трактуется как использование GPT-модели через API, а не автоматизация веб-сессии ChatGPT. Для Yandex использовать его официальный API и отдельные учётные данные.

Имена настроек, только как проектирование: LLM_PROVIDER, OPENAI_API_KEY, OPENAI_MODEL, YANDEX_API_KEY, YANDEX_FOLDER_ID, YANDEX_MODEL. Значения и файлы настроек сейчас не создаются. Адаптеры поддерживают общий контракт выбора инструмента/аргументов, завершения ответа, ссылок и черновика; результаты инструментов возвращаются агенту в одном формате. JSON, имена инструментов, аргументы и ссылки проверяются сервером независимо от structured outputs/native tool calling модели.

Автоматический fallback отвергнут: он скрывает смену качества, тарифа и получателя данных. Оператор переключает провайдера явно. При отсутствии ключа, 401/403, 429, таймауте или недоступной модели показывается причина. Для генерации допускается небольшой ограниченный повтор временной ошибки с задержкой, но не бесконечный цикл. Непригодная запись обрабатывается и без доступной LLM.

Подписка ChatGPT и API имеют отдельный биллинг; наличие Codex Desktop не доказывает доступность API. До начала интеграции нужно проверить API-ключ, оплату, доступную модель и допустимость региона эксплуатации. Россия отсутствует в официальном списке поддерживаемых стран OpenAI; размещение и доступ команды пока неизвестны. При недоступности OpenAI поддержка остаётся в проекте, а для показа явно выбирается доступный Yandex. Обход ограничений не проектируется.

### 10. Проверка и сдача в пределах 48 часов

| Часы | Результат |
|---|---|
| 0–4 | Доступные ТЗ v6, архив и PDF сверены; заглушки запускаются; контракт v6, инструменты агента, соответствие двигателей и правила качества проверены; API-доступ подтверждён. |
| 4–12 | Основа приложения, одна реальная машина/проверка, одно руководство с проверенной процедурой, минимальный поиск, ML-клиент, один доступный LLM-адаптер и простой экран; начата подготовка контрольного набора. |
| 12–16 | Первый сквозной проход через выбираемые агентом инструменты: реальная ML-проверка → объяснение в чате с источником → вопрос → предпросмотр → команда → номер ТОиР. Запреты статуса, качества и источников уже действуют; отдельно проверить сбой и вопрос только к RAG без ML/ТОиР. |
| 16–24 | Расширение до всех шести PDF, четырёх групп двигателей и всех 50 машин с историей; OCR, полный контрольный набор и приёмка поиска; второй LLM-адаптер. |
| 24–28 | Полная смысловая приёмка, контрольные ветки, мобильный интерфейс и обработка ошибок интеграций; сквозной сценарий на полном объёме P0. |
| 28–32 | Закрыть P0 на всех группах двигателей; прекратить добавлять функции. |
| 32–40 | Восемь часов на собственные проверки, ручную сверку источников и исправления. |
| 40–44 | README, измеренный пятиминутный запуск подготовленной поставки, описание компонентов, репетиция, непрерывное видео С1–С3 до трёх минут и ролик до 60 секунд. |
| 44–48 | Четыре часа резерва на критические исправления, перезапись и комплект сдачи. |

Это календарный бюджет, а не обещание 48 часов непрерывного труда одного человека. Состав команды не задан; если темп ниже, исключать P1, сохранять P0 и резерв. Работы по документам начинаются рано, потому что они несут наибольшую неопределённость.

Контрольная точка 16-го часа обязательна: если цепочка не проходит, сначала устранить её блокер, затем расширять корпус и интерфейс; подстановка готового диагноза, ответа или номера заявки не считается прохождением. Ранний проход не означает завершение P0 и не отменяет полный корпус, парк или второй адаптер.

Собственные проверки покрывают норму, пригодное отклонение, check_failed, плохое качество при ином статусе, помехи/низкую уверенность, отсутствие инструкции, общую процедуру, чужой двигатель, пустые поля, смену машины, отказ API и неопределённый результат ТОиР. Для обоих адаптеров проверяется одинаковый контракт, включая связи утверждений с выдержками. Приёмка поиска и ручная смысловая приёмка по разделам 4–5 обязательны до закрытия P0 и повторяются после затрагивающих их изменений.

Видео: около 0:00–0:20 выбор машины/проверки; 0:20–1:10 объяснение риска и источники; 1:10–1:40 вопрос по руководству; 1:40–2:15 предпросмотр и отправка заявки с номером; 2:15–2:45 сбой записи; оставшиеся секунды — запас. Конкретные машины и вопросы выбираются из выданных материалов, заранее диагнозы и страницы не сочиняются.

## Risks / Trade-offs

- [Расхождения выданных источников] → применять описанные трактовки ТЗ v6, архива и ответов организатора; полное положение, часовой пояс и формат сдачи ещё уточнить. Новые обязательства сверять до зависимой реализации.
- [Поиск по русским терминам не находит синонимы] → контрольный набор и пороги раздела 4; исправление провала обязательно для P0, способ улучшения выбирается по результатам измерения.
- [OCR и таблицы искажают нормативы] → сохранять страницу, сверять критические числа; недостоверный фрагмент не использовать как основание.
- [LLM ссылается на существующую, но нерелевантную страницу] → связи утверждений с выдержками, работы из процедурных выдержек и блокировка непроверяемой применимости; ручная приёмка всех контрольных случаев и четырёх неверных связок по разделу 5.
- [OpenAI API недоступен команде или региону] → ранняя проверка доступа; сохранённый Yandex выбирается оператором без изменения правил продукта.
- [Два провайдера увеличивают объём] → два адаптера общего контракта выбора инструментов и генерации; один ограниченный агентный цикл без тяжёлого SDK-фреймворка и автоматического fallback между провайдерами.
- [ТОиР забыла заявки после рестарта] → объяснить ограничение, не считать номер глобальным; постоянная память остаётся P1.
- [Заглушка приняла неверный по смыслу запрос] → собственная проверка и ручная сверка обязательны, успех её тестов не равен успеху приложения.
- [Открытый репозиторий и сторонние материалы] → PDF руководств и текстосодержащие RAG-индексы запрещены к размещению в открытых репозиториях; проверить исключения, текущие файлы, публикуемую историю и релизы. PDF получать отдельно, индекс строить локально. Лицензии компонентов, включая PyMuPDF, проверить отдельно; ключи держать вне репозитория.
- [План превышает темп команды] → зафиксировать P0, не начинать P1 до закрытия обязательного сценария; сохранить тестирование, презентацию и резерв.

## Migration Plan

Миграции существующего приложения нет: проект новый. После отдельной команды пользователя и начала разрешённого периода создать продукт по задачам change, сверить материалы и контракты, собрать локальный индекс, проверить оба API-адаптера и пройти сценарии. Исходные `Задача.md` и `Проблема.md` остаются неизменными.

При неудачном развёртывании вернуться к проверенному коммиту продукта и воспроизвести запуск/индекс по README. Это не означает автоматического удаления данных или переписывания истории. Перед сдачей повторить запуск из чистой копии и сохранить непрерывное видео.
